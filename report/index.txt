3. Memory speed considerations
    - To avoid memory overflow programs will focus also on having memory usage which grow linearly with the numebr of records, and not with number of record*max_payload or some arbitrarly choosen buffer size
    - For this reason i used for both reading and writing the files mmap (perfect for random accesses when reading the file the firt time and also for when we have to randomly reaccess every payload while writing the ordered file)
    - Since the writing process was extrimely volatile and no efforts in trying to parallelize multiple readings/writings was effective i choose:
        a. Alway read/write from the disk from a singlethread a time
        b. Ingnore the writing from measurments (in the graphs i'll only care about reading and sorting)
    - Further proof for that is that in different executions of the same code the writng took 68, 264 and 503 seconds

4. Single node implementations
    - The code are based on the following structure: reading the file record by record and filling a vercotr or stuct IndexRec (describe it), then ordering the vector of IndexRec, then writing the ordered file depending on the ordered vector (i read on the IndexRec where the payload is, read it from the unsorted file, then write the record in the right position of the ordered file)
    - Also for parallel version during the mergesort the task which consists in ordering an array or less than 10000 elements aresolved linearly with std::sort to avoid unnecery overhead. 10000 is thus considered as a "base case"
    - All the solutions has been programmed to have a memory usage that (thanks to the usage of the IndexRec vector) grows linearly with the number of elements ignoring the maximum payload

    4.1 Sequential code
        - Just reading the file, sorting using std::sort, then writing the ordered file, no overlap whatsoever

    4.2 FastFlow code
        - use one farm (n threads -> 1 emitter and n-1 workers)
        - if only one thread is available then we just call std::sort without using any farm
        - First task scheduled is the reading of the files
        - Then the emitter produces all the task needed for the mergesort in a recoursive way
        - as soon as a base case is reached in the recursive generation process of the tasks it's immediatly enqueued
        - To sort as soon as the elements has been read i use the ProgressGate
            - each leaf of the treee is a base case of at most 10000 elements, which knows which elements require,  so it sleeps until they have been read
            - reading worker wakes up every thread waiting every 10000 elements (best case)

    4.3 OpenMP code
        - First task scheduled is the reading of the files
        - MEANWHILE task based approach (top down recursive task generation) merge sort on the IndexRec vector
        - uses the ProgressGate as the ff code
            - each leaf of the treee is a base case of at most 10000 elements, which knows which elements require,  so it sleeps until they have been read
            - reading worker wakes up every thread waiting every 10000 elements (best case)

    4.5 Observations:
        - omp version with 1 thread is very bad (have to make sure that the task reading the file has finished using a taskwait before starting the recoursive merge task)
        - ff version with just 2 thread cant even beat the sequential cause one thread is stuck in the emitter duty, not actively ordering
        - increasing the available threads they both perform beter than the sequential and the omp is slightly better than the ff version
        - most importantyl we see from the speedup graph that the more the number of elements and the smaller the max payload the greather is the speedup. This i because i increase the time required for the sorting while having a proportionally lower reading time required
        - with very few elements with big payload we have the lowest speedup because the execution tends to be memory bound instead of processing bound
            - when i build the IndexRec vector i unse mmap, when i read one element form the disk in reality im reading a whole page, the bigger the max payload the fewer the keys in a single page => more pages need to be read => more time to fill the IndexRec vector

5. Multi node implementations
    - We use MPI, only one node uses the disk at a time tho, cause trying to overlap them didnt improve results and executing the programs while other students were executing their of the slurm server used to slow eachother disk access speed, discoraging an approach with simultanious writing from different nodes
    - One node read and build the IndexRec vector, as soon as it has number of elements/ number of avilable nodes it send them in a asynchronous way
    - Nodes receive unsorted arrays, sort them and either send them to another node or wait till another node ordered their vector and is ready to send it
    - here there is the log2 merge phase, where the number of nodes that merges is divided by 2 each time, till the starting node receive the second ordered array and do the final merge, and then write the ordered file

    5.1 Single node sorting
        - each node osrt using opm, choosen for the better performance on greater number of nodes and for the semplicity of the code
        - The merging process after receiving the already ordered array from another node is not parallelized in the other end

    5.2 Performance evaluation

    5.3 Observations
        - With one or few threads per node we gain better results by distributing the work on multiple nodes
        - While increasing the threads per node we actually lose performances by spreading the work on multiple nodes
        - This behaviours is because the faster we compute the sorting on the single node and the more is the proportion of the time we spend on sending and receiving the elements (either to sort or already sorted)
        - With 32 threads per node for example the time we spend on communication overcome the gain in performance that we obtain from splitting the work over 8 nodes. Making the execution communication bound

6. Approximative cost model for the distributed solution? Bootlenecks? comp-to-comm overlap?
    - [yet to be defined]
    - i'd like to propose as a cost model a sort of graph of dependencies which im gonna draw,something that resemble a BSP algorithm
    - something which resemble (algoritmically and ignoring the varying number of nodes):
        - reading_and_sending_cost = (file_size/reading_speed) + (IndexRec_vector_size/communication_speed)
        - sorting_and_merging_and_collecting_cost = (sort_cost(elements_num) + (IndexRec_vector_size/communication_speed)) + (merge_cost(elements_num) + (IndexRec_vector_size/communication_speed)) * log2(elements_num)
        - writing_cost = (file_size/reading_speed) + (file_size/writing_speed)
        - total_cost = reading_and_sending_cost + sorting_and_merging_and_collecting_cost + writing_cost
    - It's a simplified mathematical representation of the cost which ignores:
        - The fact that every node during the merging phase does not send all the array, but something smaller is ignored
        - The fact that the the sorting phase of the nodes stars before all the array has been read, so the nodes thends to finish before than in the expected model, but still, considering that we are searching for the longest path while extimating the cost this should end up being irrelevant logaritmichally speaking
    - With the formulas we observe that BOTH the computaton cost and che communcation cost grow with O(N*logN), so independently from N if one of the two is particularly more efifcient than the other (see cases with 1 thread per node vs 32 threads per node) both of them can end up being the bottleneck
    - Anyway, code uses MPI_Isend to overlapp reading with sending
    - And the sorting + merging is managed in a way that every node send and receive as soon as possible, without haveing global barriers where every nodes wait for all the other
